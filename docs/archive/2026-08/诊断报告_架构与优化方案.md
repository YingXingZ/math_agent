## 二、架构合理性诊断

### ✅ 合理之处

1. **三层分离清晰**：8014 知识库 → Agent 桥接 → 前端，职责分明
2. **证据优先策略**：`evidence_policy` 要求模型结果仅作候选，涉及成绩发布保留教师复核入口
3. **双重校验机制**：Qwen 视觉识别 + 独立文本求解 + SymPy 数学判等交叉验证
4. **只读桥接**：`knowledge_bridge.py` 只读取 8014 数据，不修改源库
5. **安全拦截**：`_problem_text_issue()` 在同步时过滤乱码题目，不让乱码进入作业

### ⚠️ 需要改进的问题

#### 问题 1：OCR 质量是全局瓶颈

8014 的 `content_text` 由 OCR 生成，质量参差不齐：
- **16% 的题目有 OCR 污染**（J→f、9→g、公式碎片化）
- **30% 的题目无文本**（仅图片）
- OCR 乱码通过 `_problem_text_issue()` 被拦截，但**拦截 ≠ 修复**，被拦截的题目无法参与组卷

**影响**：可用题目数量实际远低于 463，部分章节可能无足够可发布题目。

#### 问题 2：答案库完善效率低

当前流程：`答案PDF → OCR → 候选 → 教师逐题核验 → 写入 std_answer`

- 303 个候选答案积压在 `pending` 状态
- 341 题答案未验证
- `teacher_vision.html` 的候选核验 UI 是逐题操作
- 没有批量核验/自动验证机制

#### 问题 3：Agent 本地缓存与 8014 数据冗余

Agent 的 `questions` 表缓存了 8014 的题目副本，存在同步一致性问题：
- 8014 更新答案后，Agent 缓存不会自动更新
- `sync-section` 是手动触发，不是增量同步
- 缓存中 `content` 字段可能过时

#### 问题 4：前端无 LaTeX 渲染

- `teacher_portal.html` 直接显示 `escape(content)` 原始文本
- `printable_assignment` 用 `escape(r['content'])` 渲染作业单
- 含 LaTeX 的答案（如 `\frac{1}{x}`）显示为原始代码，非数学公式

#### 问题 5：8014 工作台 `_where_clause` 有 SQL 注入风险

`api_app.py` 第 486-497 行使用字符串拼接而非参数化查询：
```python
c += f" AND s.section_no='{section_no}'"  # 危险！
```

## 三、题目乱码问题 — 根因与修复

### 根因定位

乱码来源于 **8014 知识库的 `content_text` 字段**，由 OCR（Pix2Text / RapidOCR）生成时产生的以下问题：

| 乱码类型 | 示例 | 原因 |
|----------|------|------|
| 函数名误识 | `J(x)` 应为 `f(x)` | OCR 将斜体 f 误识为 J |
| 变量名误识 | `9(x)` 应为 `g(x)` | OCR 将 g 误识为 9 |
| 公式碎片化 | 单字符成行 `mh\n／\n"` | 公式图片被逐字符切分 |
| 符号污染 | `←`、`ζ`、`例1` | 数学符号被误识为其他字符 |
| 中文误识 | `J（功` 应为 `f(x` | 括号和函数名混淆 |
| 无文本 | `content_text=""` | 未执行 OCR 或 OCR 失败 |

### 修复方案（三层）

#### 方案 A：8014 源头修复 — 用 VLM 重识乱码题目（推荐）

对 8014 中 `content_text` 为空或被 `_problem_text_issue()` 判定为乱码的题目，调用远程 VLM 服务（Qwen2.5-VL）重新识别原题截图：

```python
# 伪代码：批量重识
for problem in problems_with_bad_text:
    image = load_crop_image(problem.crop_image_path)
    result = vlm_client.post("/solve-from-image", json={
        "image_base64": base64(image),
        "section_no": problem.section_no,
        "problem_no": problem.problem_no,
    })
    if result.confidence >= 0.85:
        update problem.content_text = result.problem_text
        update problem.std_answer = result.std_answer
```

**优势**：一次修复，全局受益（Agent 同步时自动获取正确文本）。

#### 方案 B：Agent 侧增强过滤 + 图兜底

在 `knowledge_bridge.py` 的 `build_image_solve_candidate()` 中：
- 已有 VLM 兜底逻辑，但 `timeout=600` 秒可能过长
- 建议将 `eligible` 阈值从 `confidence >= 0.8` 调整为分级处理

#### 方案 C：前端增加图片优先展示

在 `teacher_portal.html` 和 `printable_assignment` 中：
- 优先展示原题截图（`crop_image_path`）
- 文本仅作辅助参考
- 加入 KaTeX/MathJax 渲染 LaTeX 答案

### 具体修复步骤

1. **扫描 8014 全部 463 题**，用 `_problem_text_issue()` 标记乱码题目
2. **批量调用 VLM** 重识被标记题目的原题截图（可复用 `server_vlm_service.py` 的 `/solve-from-image` 端点）
3. **VLM 结果二次校验**：用 `grading_engine.expr_equal()` 对比 VLM 答案与现有 `std_answer`
4. **高置信度自动更新** `content_text`；低置信度进入教师复核队列
5. **Agent 侧**重新 `sync-section` 获取修正后数据

## 四、批量完善答案库方案

### 现状瓶颈

```
303 pending candidates → 逐题核验 → 效率极低
341 unverified answers → 无法自动判分
```

### 批量方案设计

#### 阶段 1：自动分类与预验证

```
对每个 pending candidate：
  1. 检查 ocr_text 质量（是否有乱码）
  2. 检查是否已有 std_answer（对比 candidate 与现有答案）
  3. 调用 grading_engine.expr_equal() 做数学判等
  4. 分类：
     - auto_approve: OCR 清晰 + 数学判等一致 + confidence > 0.9
     - auto_reject:  OCR 乱码 + 与现有答案矛盾
     - manual_review: 其余
```

#### 阶段 2：VLM 批量识别无答案题目

对 341 个 `unverified` 且无 `std_answer` 的题目：
```
1. 按章节分组
2. 加载答案 PDF 对应页面
3. 调用 VLM /review 端点批量识别
4. 自动匹配 problem_no → std_answer
5. 写入 candidate 表（不直接写 problems.std_answer）
```

#### 阶段 3：批量核验 UI

在 8014 工作台新增批量核验页面：

```
┌─────────────────────────────────────────────────┐
│ 批量核验 — 习题 1.1 (共 15 题)                    │
│ ┌─────────┬──────────┬──────────┬────────────┐  │
│ │ 题号     │ 候选答案  │ 现有答案  │ 判等结果    │  │
│ │ 1       │ (-∞,-4]  │ (-∞,-4]  │ ✓ 一致     │  │
│ │ 2       │ 不同...   │ 不同...   │ ✓ 一致     │  │
│ │ 3       │ 偶函数    │ (空)     │ → 新增     │  │
│ │ 4       │ 乱码     │ (空)     │ ✗ 需重识   │  │
│ └─────────┴──────────┴──────────┴────────────┘  │
│ [全选一致项] [批量采纳] [批量拒绝] [逐题核验]      │
└─────────────────────────────────────────────────┘
```

#### 阶段 4：教师确认后批量写入

```python
# 批量采纳逻辑
for candidate_id in selected_ids:
    candidate = get_candidate(candidate_id)
    if math_equal(candidate.ocr_text, problem.std_answer):
        update problem.std_answer = candidate.ocr_text
        update problem.answer_status = 'verified'
        update candidate.match_status = 'approved'
    elif not problem.std_answer:
        update problem.std_answer = candidate.ocr_text
        update problem.answer_status = 'verified'  # 教师确认后
        update candidate.match_status = 'approved'
```

## 五、Agent 架构优化建议

### 5.1 与产品路线的契合度

用户目标路线：
```
8014 知识库 → 高数教材智能体（组卷、批改、讲解、反馈）→ 教师端/学生端
```

当前实现：
```
8014 知识库 → knowledge_bridge → Agent(local cache) → teacher_portal / student_submit
```

**契合度评估：75%** — 基本符合，但缺少"讲解"和"反馈"环节。

### 5.2 建议补充

| 功能 | 当前状态 | 建议 |
|------|----------|------|
| 组卷 | ✅ 已实现 | 加入教师手动选题模式 |
| 批改 | ✅ 已实现 | 优化 VLM 调用超时和重试 |
| 讲解 | ❌ 缺失 | 新增 `/api/agent/explain` 端点，用 VLM 生成解题步骤 |
| 反馈 | ⚠️ 部分 | `grading_experiences` 表已建，但未用于反馈生成 |
| 作业PDF生成 | ✅ 已实现 | 加入 LaTeX 渲染（当前是纯文本） |
| 难度分层 | ✅ 已实现 | 保持 |

### 5.3 数据流优化

**当前问题**：Agent 缓存 ↔ 8014 同步是手动的、全量的。

**建议改为**：Agent 不缓存题目文本，每次组卷/批改时实时从 8014 检索。理由：
1. 8014 是唯一数据源，缓存引入一致性问题
2. 463 题的数据量不大，实时检索延迟可控
3. 减少代码复杂度（去掉 `_sync_section_into_local_cache`）

### 5.4 安全修复

`api_app.py` 的 `_where_clause()` 函数存在 SQL 注入：
```python
# 当前（危险）
c += f" AND s.section_no='{section_no}'"

# 修复（参数化）
c += " AND s.section_no=?"
args.append(section_no)
```

## 七、总结

当前系统的**三层架构方向正确**，证据优先策略和双重校验机制设计合理。主要瓶颈在于：

1. **OCR 质量瓶颈**：16% 题目乱码 + 30% 无文本 → 用 VLM 批量重识可解决
2. **答案库效率瓶颈**：303 候选积压 + 341 未验证 → 用自动判等 + 批量核验可解决
3. **前端渲染缺失**：LaTeX 不渲染导致"看起来像乱码" → 加 KaTeX 可解决

核心思路：**VLM 重识 → 自动判等 → 批量核验 → 教师确认**，将逐题操作变为批量操作，效率提升 10x+。
