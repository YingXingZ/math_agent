# 高数作业工作台 · 功能现状分析与改进规划

> 基于实际代码（`api_app.py` / `grading_engine.py` / `difficulty_tier.py` / `extract_book.py` / 两端 HTML）的审计结论。

---

## 一、当前功能现状总览

### 已具备的能力
| 能力 | 状态 | 说明 |
|------|------|------|
| 题目提取（OCR+原图裁切） | ✅ 可用 | 34 节、136 题入库；刚修复提取截断 bug，v4 重提中 |
| 知识点标签 | ✅ 刚修复 | 已补全 1~4 章细粒度标签（不再是 ch2.overview） |
| 难度分层 | ✅ 可用 | basic/medium/advanced 三档，difficulty 1/3/5 已落地 |
| 作业发布 | ✅ 可用 | 按难度比例选题（基础3+提高2+拓展1） |
| 学生提交 | ✅ 可用 | 文字 + 拍照手写图片 |
| 批改接口 | ⚠️ 已接线但空转 | `/grade/auto`、`/grade/batch` 接好，但无标准答案，无法真实判分 |
| 人工复核抽样 | ✅ 可用 | `/review/sample`、`/review/stats` |
| 学期成绩报表 | ✅ 可用 | `/reports/semester`，CSV 导出 |
| 六大前端模块 | ✅ 可用 | 题库/作业/提交/批改/复核/报表 |

### 技术架构
- **后端**：FastAPI + SQLite（`api.db`）
- **前端**：单文件 HTML（教师工作台 + 学生提交页）
- **OCR**：RapidOCR（提取阶段 + 可复用于手写）
- **批改**：SymPy 符号计算
- **数据模型**：`problems`（题目）、`submissions`（提交）、`homeworks`（作业）、`classes`/`students`

## 二、具体改进点（价值 + 优先级）

### 改进 1：让自动批改真正可运行（补标准答案）— **P0 最高**
- **现状**：`/grade/auto` 创建 `ProblemSpec(std_answer="", steps=[], ptype=...)`，把学生答案与**空字符串**比较，几乎必判错误。
- **价值**：自动批改是系统核心价值主张，目前形同虚设，必须首要修复。
- **优先级**：P0
- **工作量**：中（加 `std_answer` 列 + 录入/生成答案 + 改造接口读取）。

### 改进 2：手写图片 OCR 识别 — **P0/P1**
- **现状**：学生拍照上传的图片只存 URL，**不做 OCR**，无法参与文字批改。但多数学生手写作答。
- **价值**：没有 OCR，批改对图片提交 ≈ 零覆盖。
- **方案**：提交时/批改前对图片跑 RapidOCR → 文本 → 喂给 SymPy。
- **优先级**：高（与改进 1 配套才有意义）。

### 改进 3：用户反馈 / 申诉机制 — **P1**
- **现状**：无任何"判错反馈/评分异议/标准答案纠错"入口。
- **价值**：收集错误样本，用于迭代答案库与题型识别，形成数据飞轮。
- **方案**：学生"我要申诉"、教师"标记标准答案有误"、批改结果点赞/踩。

### 改进 4：题目内容结构化（抽取题面文字）— **P1**
- **现状**：`problems.content_text` 基本为空，仅存裁切图路径。
- **价值**：支撑知识点自动推断、错题检索、相似题推荐、VLM 答案生成。
- **方案**：提取阶段对裁切图做 OCR 写入 `content_text`。

### 改进 5：题型自动识别（calc/proof 区分）— **P1**
- **现状**：全部 136 题 `ptype='calc'`，证明题未区分，导致证明题也走计算题逻辑（且空答案）。
- **价值**：证明题需走"建议分+人工"策略，识别错误会误判。
- **方案**：根据版面特征（"证明"/"证："+题、无具体数值结果）自动判题型；引擎本身已支持 proof 分支。

### 改进 6：性能优化 — **P1/P2**
- **现状**：提取阶段 329 页 OCR 约 25 分钟，无进度持久化/断点续传；API 无缓存，图片每次从磁盘读。
- **价值**：长任务易失败、教师等待体验差。
- **方案**：提取任务异步化 + 进度条；热点查询缓存；图片缩略图/懒加载。

### 改进 7：可扩展性 — **P2**
- **现状**：硬编码单教材、单 venv、相对路径（如 `extract_img`）。
- **价值**：限制多班级/多教材复用。
- **方案**：多教材配置表；配置外置；容器化部署。

### 改进 8：数据分析与教学洞察 — **P2**
- **现状**：只有基础计数 + 学期报表。
- **价值**：薄弱知识点预警、班级对比、个性化作业。
- **方案**：错题聚类、知识点掌握度热力图、学生画像。

### 改进 9：标准答案自动化生成 — **P2**
- **价值**：降低教师录入成本。
- **方案**：VLM 读题图生成答案草稿，教师确认后入库。

## 三、自动批改专题分析

### 3.1 当前是否已支持？
**结论：架构已支持，功能未就绪。**

- `grading_engine.py` 本身是**成熟可用**的：
  - 三级表达式判等：符号化简（置信度 0.99）、数值容差（0.95）、随机取点（0.90）
  - 步骤匹配（正则命中关键步骤给过程分）
  - 证明题建议分 + 强制人工复核
- 但 `api_app.py` 的 `/grade/auto` **没有把标准答案喂进去**：
  ```python
  spec = ProblemSpec(pid=pid, ptype=ptype, max_score=10.0,
                     std_answer="", steps=[], keywords_required=[])
  ```
  → 学生答案与空串比较，结果几乎必为"错误/低置信"。
- `problems` 表**没有 `std_answer` 字段**，且 136 题 `ptype` 全为 `calc`。
- 学生手写图片**未 OCR**，无文本可判。

**所以当前系统整体批改准确度 ≈ 0**（不是引擎不行，是缺配置与数据）。

### 3.2 目标工作流程
1. 学生端提交 `{problem_id, text | image}`
2. 若是图片 → RapidOCR 识别为 text
3. 服务端按 `problem_id` 取 `std_answer / ptype / steps`
4. 计算题：`expr_equal(学生, 标准)` → 答案分 + 步骤分；
   证明题：步骤/关键词覆盖率 → 建议分，`need_review=True`
5. 置信度 < 阈值（0.85）→ 转人工
6. 结果回写 `submissions` + 反馈给学生/教师

### 3.3 支持题型范围
| 题型 | 机制 | 准确度 | 备注 |
|------|------|--------|------|
| 计算题（数值/表达式） | SymPy 符号/数值/随机点判等 | 高（0.90~0.99） | 极限、导数、积分、方程；2/3≈0.6667 友好容差 |
| 证明题 | 步骤匹配 + 关键词 → 建议分 | 不自动定分 | 强制人工终审 |
| 纯文字论述 / 几何作图 / 开放题 | 不支持 | — | 需 LLM，一致性难保证 |

### 3.4 评分准确度（引擎本身）
- 计算题：符号化简判等 **0.99**；数值判等 **0.95**；随机取点 **0.90**
- 含步骤规则时：答案错但步骤对 → 保留过程分（提示计算失误）
- 当前系统整体准确度：**≈0**（缺标准答案所致）

### 3.5 配置方式（让批改真正可用）
1. `ALTER TABLE problems ADD COLUMN std_answer TEXT`
2. 录入/生成每题标准答案（教师录入 或 VLM 生成草稿）
3. 标注 `ptype`（calc/proof）与 `steps`（关键步骤正则）
4. 改造 `/grade/auto`：从 DB 读取上述字段构建 `ProblemSpec`，而非硬编码空值

### 3.6 实现自动批改所需核心能力
| 能力 | 说明 | 复杂度 |
|------|------|--------|
| A. 标准答案库（数据） | 最大成本，可 VLM 辅助生成 | 中（数据） |
| B. 手写 OCR 接入 | 已有 RapidOCR，需串联流水线 | 中 |
| C. 题型自动识别 | 版面特征判断 calc/proof | 低~中 |
| D. 主观题评分策略 | 证明题已实现建议分；论述题需 LLM | 高 |
| E. 结果反馈与申诉 | 前端+接口，低成本 | 低 |

### 3.7 技术可行性与复杂度评估
- **计算题自动批改**：✅ 可行，**复杂度中低**，1~2 周可上线（主要工作量在标准答案录入 + 接口改造）。
- **手写 OCR 批改**：✅ 可行，**复杂度中**，OCR 已具备，关键是流水线串联与识别纠错。
- **证明/论述题自动定分**：⚠️ 部分可行（建议分已支持），**完全自动定分难**，依赖 LLM 且需人工兜底，**复杂度高**。
- **端到端全自动**：❌ 不现实，应采用 **"机器初判 + 人工终审"** 混合模式。

## 四、一句话总结
系统"骨架齐全、血肉不足"：**提取、分层、作业、报表**已可用；**自动批改**引擎优秀但被"缺标准答案 + 无手写 OCR + 无题型标注"三道数据鸿沟卡住，是当前最高优先级的修复点。
